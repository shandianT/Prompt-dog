# 验证设计与迭代闭环手册

S3≥1、设计闭环、或交付前自检时读。核心原则：验证是保险，保费不应超过标的——错误代价决定验证强度，而不是「越多越好」。

## 验收标准确认卡（仅 S3≥1 时出）

本卡不单独增加轮数：计入总轮数预算，优先并入最后一轮澄清卡合并发出；已在澄清轮确认过的项禁止重复问，能从已答项或场景推断的项直接转 ★预填或假设（用户明说「错了要出大事」，Q1 就预填 C 不再问）。S3=0 时不出卡，由你自拟标准写入产物并标注假设——但验收标准区块 L2 及以上产物必有。

```markdown
## 确认卡片 · 验收标准
回复编号即可（如「1C 2A 其余默认」），或「都按推荐」。

**Q1 这个任务的错误代价？**
- A. 低——错了改一下就行
- B. 中——错了会浪费别人时间
- C. 高——对外发布/影响决策，出错有实际损失
（★ 由你按场景推断预填到对应档位，并附一句推断理由；本题为穷尽枚举，不设「其他」）

**Q2 输出的量化要求？**
- A. <按场景推测的建议值，如「800 字内、3–5 个要点」> ★推荐：<理由>
- B. <备选值>
- C. 其他（一句话）

**Q3 格式要求？**
- A. <按场景推测，如「markdown 表格 + 结论段」> ★推荐：<理由>
- B. 纯文本
- C. JSON/结构化数据
- D. 其他（一句话说明）

**Q4 红线（绝不允许出现的）？**（可多选）
- A. 编造数据/来源 ★默认勾选：任何场景下编造都直接摧毁产出可信度
- B. <场景化红线，如「提及未公开客户名」>
- C. 无其他红线
- D. 其他红线（一句话说明）
```

**Q1 预填规则**：★ 由你按场景推断预填，不默认「低」——用户不确定时低估风险会跳过必要验证。**仲裁规则：你的场景推断与用户自评取其高**；用户选 A 但产出对外发布/供决策时，按 C 处理并说明一句原因。答案联动：澄清中途出现升险信号（如「受众改成管理层」），错误代价随之上调并告知。

## 验证机制选型表

| 机制 | 触发信号 | 插入位置 | 成本 |
|---|---|---|---|
| 自我一致性 | 客观有正解 + 错误代价中高（计算、分类、抽取） | 生成时：3 次独立推理→投票 | 3 倍 token |
| 交叉核查 | 含可查证的事实陈述（数据、日期、引用） | 生成后：调工具逐条核对 | 中，需搜索工具 |
| 来源引用强制 | 内容对外发布或供决策 | 生成中：无来源的关键论断标 [待核实] | 低 |
| 对抗审查 | 错误代价高的最终交付物 | 交付前：「专门找茬的反方」跑一遍列反驳清单 | 中，1 轮额外调用 |
| 人工确认点 | 不可逆动作（发送、发布、删除）或红线边缘 | 动作执行前：暂停并出确认卡片 | 极低，但打断流程 |

**配比原则**：代价低 → 最多一种轻量机制；代价中 → 1–2 种；代价高 → 强制「来源引用 + 对抗审查 + 人工确认点」，含可查证事实陈述时必加交叉核查。向用户呈现严格档选项时标注成本（「耗时约多一倍」），让他有知情选择权。

## 会话内试跑（交付前质检，L2 以上必做)

1. 默认自行构造样例输入并标注「试跑样例」，不向用户索要——别让交付卡在等材料上；交付时附一句「有真实样例贴来，我可再跑一遍替换结论」。
2. 用生成的提示词（L2 取关键步骤、L3/L4 取首环节）实际跑一遍。
3. 对照验收标准逐条检查输出：格式是否符合数据契约、标准是否可达。
4. 不达标就地修正提示词，最多修 2 轮；仍不达标说明设计有问题，回到构建阶段而不是继续硬调。
5. 交付时附一句试跑结论（「已用样例输入试跑，验收标准 N/N 通过」）。

试跑是你在会话里做的质检，别与产物内嵌的运行时闭环混淆。

## 诊断分支表（症状 → 根因 → 精调 → 回到哪一步）

评估未通过时先归类症状再动手，禁止盲目重写：

| 症状 | 根因判断 | 精调策略 | 回到哪一步 |
|---|---|---|---|
| 结论/逻辑/计算错 | 推理深度不足 | 加 CoT；仍错→自我修正；需外部事实→ReAct | 回构建，改提示词 |
| 结构/字段/语气不对 | 输出控制缺失 | 输出格式化（给 schema）+ 响应预填充；创造性失衡→参数调优 | 回构建，只改输出段 |
| 长输入后忘记前文要求 | 上下文丢失 | 关键指令置尾、分块 + 提示链 | 回架构，可能升级 |
| 大体对、细节瑕疵 | 无结构性问题 | 建设性引导：对话中直接微调 | 就地修，不回退 |
| 反复摇摆、时对时错 | 稳定性不足 | 少样本补例 + 自我一致性 | 回构建 |
| 修改后复杂度实质变化 | 判级过期 | 重算六信号 | 回判级（见 SKILL.md 变更与重判级） |

## 终止条件模板（写入每个 L3/L4 产物）

```markdown
## 循环终止条件
- 最大轮数：3 轮（每轮 = 执行→评估→诊断→精调一次）
- 收敛通过：验收标准全部打钩 → 交付
- 提前止损：打钩数连续 2 轮不增加 → 触发降级
- 降级路径：缩小范围，交付已达标部分 + 未达标项清单
- 上报路径：降级仍不可行 → 输出卡点报告（症状/已试策略/建议人工介入点），停止自动迭代
```

「无改善」的唯一度量是验收标准打钩数——不用「感觉没变好」这类不可判定的表述。

## 诊断改进模式的回归对照

改进现有提示词交付时，附一个最小回归样例：同一测试输入下「原版预期表现 vs 改进版预期表现」各一句，并建议用户用自己的真实输入各跑一次对比——改进必须可验证，不能只靠评分数字。

## 交付前自检清单（每次交付都跑）

```markdown
□ 产出形态与复杂度等级匹配（没有用 L3 大炮打 L1 蚊子）
□ 验收标准区块存在，且与用户确认的卡片一致（豁免场景除外）
□ 错误代价≥中的内容已内嵌对应验证机制
□ L3/L4 含内嵌闭环且终止条件写死、「无改善」可度量
□ 全程未出现连续开放式提问；每张卡片都有推荐默认值
□ 提示词本体自含（拿走即用，不依赖本次对话上下文）
□ 头部有版本行 + 生效假设清单（每条带依据）
□ L2 以上已会话内试跑并附结论
□ 编排产物只使用运行环境真实存在的能力
```
