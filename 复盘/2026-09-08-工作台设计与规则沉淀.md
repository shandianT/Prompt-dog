## 结论

- **画布是中心，聊天窗口不是。** 工作台的主对象是流程图，工作狗是图的派生物。已抬升 → `design/workbench/产品定义.md`
- **两个建议的决定**：楔子 = 投标流程；运行模型 = 工作台是壳，引擎是用户自己的 Claude Code / Codex。已抬升 → `产品定义.md`（待拍板）
- **八条原则**是原型的判断标准。已抬升 → `SPEC.md` §3、`references/process-rebuild.md` 末尾
- **流程重构是 PromptDog 的一个入口模式**，不是判级对象：先出图与诊断，打包建议里的每只狗再判级。已抬升 → `SKILL.md` 入口路由、`references/process-rebuild.md`
- **流程图 JSON 是技能与画布的共同契约**：技能产出它，画布渲染它，复盘回流改它。已抬升 → `design/workbench/flow.schema.json`
- **设计文档 vs PRD**：设计文档定「画什么、怎么交互、按什么判断」，PRD 定「为谁、解决什么、怎么算成功、不做什么」。AI 时代留下的是：一页产品定义、可二值判定的验收、按依赖排序的小故事、状态文件；丢掉的是：长 PRD、评审会、事无巨细的原型标注。已抬升 → `产品定义.md`（一页）+ `stories.json`（可执行的 PRD）
- **「一句话 + 材料」**：一句话给方向，材料给现状；材料决定现状图八成质量，所以首页贴材料入口要醒目。已抬升 → `SPEC.md` §5 01 首页、`process-rebuild.md` 第 0 步
- **沉淀原则**：集合做日志（追加、趁热），分类做资产（按谁在什么时候读分，不按主题分）；判断标准是「明天新开会话，agent 不看聊天记录能接着做」。已抬升 → `复盘/README.md`

## 追加 · 设计模块与产品主线

用户追问：怎么保证每次都能输出高质量的设计文档和 PRD、配好看的图、画图技能怎么集成、设计模块作为导航项、交付物怎么回流提高 PromptDog、功能怎么协作与串并联、产品本身的一套流程。

做法：三位设计者（质量与评测 / 产品流程与系统 / 资产飞轮与协作）各出方案，三位评委按 七问 / 一致性 / 可判定 / 最短路径 / 可落地 打分。质量与评测方案胜出，嫁接另两份的：对抗审查四视角（老板 / 搭建者 / 执行者 / 反方，名字沿用产品定义角色表）、验收先于撰写、停机标记三值语义、交接表补三行、回流门槛三条、复盘用例。评委一致删掉的：卡片里的「图」题（档位由环境决定，转 H）、不能从 flow JSON 渲染的屏幕流图 / 状态机图 / 交接图、设计文档的「五个数字」首行（改为五问首行）、给未触发的回流预留段落。

结论与落点：
- 高质量靠机制不靠运气：范例（`design/workbench/` 三件套）+ 可打钩门槛 + 四视角对抗审查 + evals 回归。已抬升 → `references/design-mode.md`、`output-templates.md`「设计模式产物」、`verification.md` 必带项两行、evals 11–13
- 图的档位由环境决定，四个镜头都从同一份 flow JSON 派生。已抬升 → `process-rebuild.md`「图档位由环境决定」、SKILL.md 与 verification.md 环境封顶段
- 设计模块 = 入口路由一行 + 侧栏一项 + 屏 11。已抬升 → SKILL.md、SPEC.md §4 §5、stories.json S16
- 交付物回流只对重复的事，九类交付物各有落点与触发条件。已抬升 → `复盘/README.md` 回流表
- 串联契约 = 上游停机标记是下游启动条件；并联只在两处合法。已抬升 → SKILL.md 主循环
- 产品主线 = 四入口 → 一个主循环 → 上岗 → 复盘 → 回流。已抬升 → SKILL.md 主循环 ⑦⑧⑨、`design/figures/product-process.svg`
